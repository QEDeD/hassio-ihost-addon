# Single-dongle trial and recovery transitions — draft, 2026-09-19

**Current decision:** the latest host-state recovery path is substantially supported, but a guaranteed state-preserving production-radio rollback is not established. In particular, we have no verified evidence that the old radio application will initialize successfully after the candidate creates a persistent PSA binding key. A one-dongle trial would still accept a possibility of prolonged Zigbee/Thread outage and additional recovery or re-pairing. Do not describe it as an assured reversible update.

This is an offline decision draft for the parent task's review. It authorizes no production interruption, flash, binding, restore or publication. No spare is assumed. Bootloader and Secure Engine stay unchanged. No erase, debug unlock, improvised unbind/replacement-key generation, automatic plaintext fallback, or speculative storage migration is part of the base trial. The specifically assessed vendor recovery branch below could be added only after offline artifact qualification and explicit approval of its one-key deletion and subsequent rebind.

## What changes, and what can be recovered

The **host stores** hold the existing networks, keys, identity records and saved counters. The **radio application** supplies the shared 802.15.4 transport. Its **persistent radio storage** separately holds CPC binding material and may contain manufacturing/configuration state. Restoring a host backup changes only the first of those; flashing an application does not prove that the third survives or remains readable by the old application.

Current evidence:

- [Zigbee loader results](token-schema/RESULT-20260919.md): the exact corrected candidate preserves all26 original nonempty synthetic token records. The exact retained old host preserves those records, including invented advanced counters and restored EUI64, on return. It discards new trust-center/key additional-info records and shrinks secondary child arrays. This supports the tested existing-network state path, not a lossless downgrade after using new features or proof of actual network operation.
- [Thread settings results](thread-state/README.md): actual old/new storage implementations preserve all tested records across both directions; network-info/counter representation and save-ahead behavior are unchanged in inspected source. Preserve the **whole latest store**, not merely an active dataset or an old snapshot. Counter margins do not authorize rewinding after traffic.
- [Functional state map](FUNCTIONAL-STATE.md): radio EUI can select the Thread settings filename; Zigbee restored-EUI handling is host-side. An unexpected identity/store selection is a stop condition. Matter fabric and actual Z2M data must remain protected even though this trial does not intentionally modify them.
- [Candidate package](../firmware/package/README.md): application-only GBL3 avoids bootloader/SE payloads and the candidate's declared NVM pages. Its first application startup still initializes NVM3/PSA; package ranges do not prove storage-read-only startup.
- [Rollback artifact](rollback/README.md): official SONOFF MultiPAN4.6.0/115200 image matches model/version/baud, but is not proven identical to the installed application or physically tested as recovery here.
- [CPC security evidence](../CPC-SECURITY.md) and [radio storage decision](DECISION.md): first binding imports persistent PSA key0x4200; candidate uses ITS V3. Baseline storage layout and behavior after that creation remain unresolved. Old host plaintext mode does not itself make old **radio firmware** compatible with new storage.

## State-transition decision table

“Candidate transmitted” begins conservatively when a restored Zigbee/Thread stack is enabled, even if user-visible traffic has not yet been observed. A restarted baseline also advances the latest state. Record every owner and state-copy transition; elapsed time alone is never evidence that no frames were sent.

| State reached | Consequential state / evidence required | Permitted continuation within an approved trial | Recovery and remaining uncertainty |
|---|---|---|---|
| **S0 — before any flash** | Current firmware/radio storage unchanged. Stop Z2M then the focused app, confirm both stopped and serial released. Capture fresh coherent stopped app/Z2M state plus complete options; retain immutable pre-trial copies. | Confirm backup checks and gates, then exactly one candidate application upload. Keep candidate working state separate from the immutable copy; same live volume with protected checkpoint is acceptable under the established switch procedure. | On backup/stop/install-preflight failure, restart the existing host/radio pair with unchanged current state. No firmware recovery needed. If baseline resumes, that resumed state becomes authoritative; an earlier checkpoint is no longer automatically current. |
| **S1 — candidate flashed, no binding attempted** | App bytes changed. Bootloader upload success and candidate CPC probe recorded. Candidate startup may already have touched NVM3/PSA. No network clients started; host network state remains frozen. Do not start normal encrypted CPCd merely to inspect versions: missing-key behavior can create a key. | Probe only with the established flasher CPC method, inspect expected version/target. If expectations hold and gate6 covers binding, run one explicit ECDH binding invocation. | On upload/launch/probe failure, one approved application-only old-GBL upload using the preserved bootloader, then matched old host with the stopped baseline data. This is a plausible route, not proven preservation: old storage startup remains unknown even before binding. If bootloader cannot be reached or rejects the retained old GBL, stop; no force/erase/bootloader update. |
| **S2 — binding attempted; result partial or ambiguous** | Radio may already have committed its persistent key while host completion failed. File absence, valid-looking file length or a timeout cannot establish whether the radio is unbound. Preserve every resulting private key file and redacted diagnostic before changing anything. | No second bind. If the original resulting file passes existing preflight, one ordinary **transport-only** connection attempt with that same file may establish whether it matches. If it succeeds, treat state as bound and proceed to S3. No Zigbee/Thread clients yet. | If the file is missing/mismatched or transport still fails, stop. The serial flasher does not provide key recovery. An already-approved old-firmware attempt remains conditional on unknown old-radio behavior after partial PSA writes. The ordinary candidate denies unbind. A separately qualified and explicitly approved vendor recovery branch R1 below can address a committed candidate binding whose host key was lost; the offline artifact is now built and checked, but physical acceptance and explicit execution approval remain outstanding. Do not improvise that branch, delete evidence or generate another host key. |
| **S3 — encrypted binding and transport succeed; stacks still stopped** | One persistent radio binding + matching private host key now exist. Validate encrypted shared endpoint/session, not process liveness. Make a second protected key copy and privately verify byte equality, permissions and identity association. | Restart only CPCd once with the unchanged key to test reconnection. A single specifically approved dongle power cycle here can test persistence before network traffic; if omitted, power-cycle persistence remains unverified. Then start the matched candidate host stacks with the preserved working stores, followed by Z2M. | If persistence/reconnection fails, preserve key and state and stop, with the same post-binding radio uncertainty as S2. Original host network snapshot is still appropriate only because no network stack has been enabled. Successful binding does not certify old-radio startup or preservation of this key across downgrade. |
| **S4 — candidate stacks enabled / candidate may have transmitted** | Candidate has the latest host stores/counters; never select an older snapshot merely because it is “known good.” Check effective identity, expected settings file, existing memberships, fresh device reports and no network-formation/reset behavior. Capture latest stopped state before any image/firmware recovery. | Permit only existing-network operation and the bounded acceptance checks below. No pairing, leave/form/reset, key rotation, new security features or configuration migration outside scope. If accepted, retain candidate with its key and update recovery record. | Preferred host-state recovery is the latest complete compatible Zigbee/Thread store with the matched old host, keeping an untouched copy before the old loader rewrites it. Exact synthetic tests support counters/keys/EUI retention; new additional-info and secondary-child data are lost by the old loader. Real semantic compatibility and radio startup remain hardware risks. If latest state is missing, corrupt or inaccessible, stop rather than restoring pre-trial counters. |
| **S5 — rollback old radio starts, old host reconnects** | Preserve the latest candidate state and key independently. Start old host against its working copy of latest compatible stores; require old radio version plus expected identity and fresh Zigbee/Thread/Matter behavior. Old host may remain plaintext as its documented baseline configuration. | Close as a failed candidate trial with verified extent of baseline recovery. Keep candidate key; plaintext success does not prove it survived in radio storage. Rebaseline current counters/state after any traffic. | Do not perform an extra candidate reflash/rebind to prove symmetry or tidy up. Record newer-state losses and whether any intended behavior failed. A process being “started” is insufficient evidence of network recovery. |
| **S6 — rollback upload, old-radio launch, or old-host attachment fails** | Determine separately whether bootloader upload failed, old CPC firmware failed to initialize/respond, or the host failed to attach with current stores. Preserve both generations of host state and the original candidate key. Stop clients to prevent repeated writes/restarts. | Only an explicitly preapproved final return to the **same candidate application and same key**, if bootloader remains reachable, may be considered after diagnosing which boundary failed. That is forward recovery, not permission for another binding or host snapshot rewind. Do not assume the old application left the key intact. | Otherwise stop with an unresolved outage. A dead/mismatched binding, inaccessible NVM, rejected old image or unreachable bootloader has no proven repair inside this plan. Additional vendor-assisted recovery/hardware access may be needed; no finite outage guarantee or no-re-pairing guarantee is justified. |

**Critical unsupported assumption:** “The old host uses plaintext, therefore binding cannot prevent rollback” is false reasoning. Plaintext only removes the old host's need for the CPC key. The old radio must still boot after newer NVM3/PSA writes, initialize its own storage without damaging relevant state, and expose the expected CPC application. Neither host-state fixtures nor the GBL payload ranges establish that chain.

## Timing and acceptance checkpoints

Proposed limits for an approval discussion, not measured maximum boot or recovery durations:

| Checkpoint | Target / decision |
|---|---|
| Before window | Complete all preparation and six gate dispositions. No dependency downloads, image builds, broad investigation or tool installation during the outage. Reserve an attended60-minute window; state explicitly that severe recovery failure can exceed it. |
| T+0 | Record health/identities, stop owners and capture coherent stopped state. Stop before flash if this is not complete within10minutes. Restart unchanged baseline where safe. |
| Next5minutes | One candidate upload and CPC probe. Let an active vendor flash operation finish or report its own failure; a planning timeout is not a reason to interrupt flash power. No blind repeated upload or automatic force flags. |
| Next5minutes | One binding attempt, protected key copy and transport-only reconnect. Ambiguous binding enters S2 immediately. If a planned physical power-cycle step is included, account for it here before enabling stacks. |
| Next5minutes | Start preserved networks; require expected identities/store selection, Thread attached state and representative fresh Zigbee/Matter behavior. An identity mismatch or unsolicited new network is an immediate stop, not a reason to re-pair. |
| Next10minutes | Observe existing powered devices, one non-actuating Zigbee read and fresh Thread/Matter reports. Check discovery through the intended HA path. Compare against baseline known failures; avoid load-switching/group tests unless separately included. |
| By about T+35 | Decide acceptance or begin the defined recovery path. Capture latest stopped state first if S4 was entered. Do not extend a failing candidate indefinitely to avoid the decision. |
| Remaining reserved window | One old-image recovery attempt, followed by identity/current-state/traffic verification. If unsuccessful, apply S6 and stop at the agreed scope boundary. Do not report “recovered within an hour” unless actually observed. |

Acceptance means existing Zigbee and Thread/Matter networks operate with preserved identities, encrypted CPC establishes with the saved key, selected fresh communication checks pass, and no unexplained repeated service failure occurs. A transport-only reconnect precedes network enablement; a subsequent controlled full-host restart is a separate acceptance step to include only if the agreed window permits it and the initial traffic window is healthy. If omitted, report restart qualification incomplete. Ten minutes is a bounded initial observation, not proof of long-term reliability or a fix for historical light/mesh failures.

The interruption includes Zigbee and Thread transport; existing endpoint power/load state should not be deliberately changed. Matter fabric stores are preserved. HA/Matter process restarts or a full-system restore are not automatic steps.

## Concrete recovery improvements using existing tools

1. **Stage both application uploads before any interruption.** Reuse universal-silabs-flasher1.1.0, the exact RTS/DTR method already observed working on this dongle, and both hashed GBLs. Its documented commands provide probe/GBL inspection/flash; they do not provide a serial radio-NVM backup or restoration mechanism. Retain normal validation; pre-authorize only any specifically required cross-flash/downgrade flags, never `--force`. [Pinned flasher documentation](https://raw.githubusercontent.com/NabuCasa/universal-silabs-flasher/v1.1.0/README.md)
2. **Keep binding separate from host network startup.** Use vendor CPCd's explicit ECDH operation only once on the trusted local physical link, with a prepared private persistent key destination. Use the existing candidate key preflight before every normal CPCd start. Preserve the resulting file immediately and test the same key through reconnect before enabling network stacks. This narrows failure attribution and avoids spending network counter margin while discovering a transport failure. The vendor documents binding replacement restrictions and default-denied unbind. [CPCd4.9.1](https://raw.githubusercontent.com/SiliconLabs/cpc-daemon/v4.9.1/readme.md)
3. **Carry current host state forward through image changes.** Reuse the existing in-place image-switch and stopped-state capture pattern, supported Supervisor backups, ordinary protected copy/verify operations, and the metadata-only descriptor check. Keep immutable pre-trial, latest-candidate and post-recovery copies separately; no custom token migration service is needed. Do not restore the whole HA/Matter system merely to change one radio app.
4. **Use existing Commander capabilities only when their prerequisites truly exist.** Commander can read memory to a private file, but its official documentation requires a working debug connection, normally J-Link. NVM3 read/parse/write tooling exists; this does not establish a USB-serial backup route, access to a locked dongle, safe restoration ranges, or correctness across PSA layouts. No probe/debug authorization or wiring is established here. Do not invoke unlock/erase to obtain it. [Memory read requirements](https://docs.silabs.com/simplicity-commander/latest/simplicity-commander-commands/memory-read-commands), [NVM3 tools](https://docs.silabs.com/simplicity-commander/latest/simplicity-commander-commands/nvm3-commands)
5. **Prepare the vendor one-key recovery application as a bounded optional branch.** Inspection below identifies a single persistent CPC-key deletion path, making this materially narrower than mass erase. Qualifying that artifact could reduce host-key-loss risk and support recovery forward to the candidate. It does not restore arbitrary old radio storage or prove old-firmware compatibility. Preparation and eventual explicit authorization are separate from execution. [Vendor recovery note](https://raw.githubusercontent.com/SiliconLabs/cpc-daemon/v4.9.1/readme.md)

### R1 observable confirmation over existing CPC

Inspected host source is the retained CPCd4.9.1 commit `87f6dbda4eef05e4538589c195099c3daf8f6f6b` under `/sdk2026-native/cpc-daemon`.

- `security/private/thread/security_thread.c:55–61` skips `security_load_binding_key_from_file()` in `MODE_BINDING_UNBIND`. `security/private/keys/keys.c:274–312` initializes crypto/RNG state but initializes an ECDH keypair only in ECDH binding mode. Therefore this explicit unbind operation does not require a lost binding key, generate a replacement binding file, or perform another binding. This exemption is specific to `--unbind`, not permission to start normal CPCd with a missing key.
- `security/private/protocol/protocol.c:148–175` sends the standard unbind request and checks the returned status. `SL_STATUS_OK` reports successful deletion; `SL_STATUS_NOT_INITIALIZED` reports that the secondary was already not bound and exits successfully. Permission, other secondary errors or request failures are fatal. Preserve the status distinction and exit result, with protocol traces/key-bearing logs disabled.
- Secondary `cpc/src/sl_cpc_security.c:743–766` uses the recovery callback to permit that request, runs the same single-key path, and returns its status. The standard system/security negotiation endpoints operate without the encrypted application session; the recovery application has no Zigbee/Thread network stack.

Proposed command form, **not executed**, using the same target UART115200/no-flow-control and an explicitly private recovery configuration:

```sh
/usr/local/bin/cpcd --conf /PRIVATE/RECOVERY/cpcd.conf --unbind
```

Invoke the binary directly with normal app/network services stopped, not through the candidate's normal service graph. The ordinary missing-key preflight belongs to normal operation; the audited explicit unbind mode intentionally does not load a key. Keep the recovery CPC socket location private and expose no TCP bridge/network service. One owner, one request, no automatic retry. The command is itself the expressly approved one-key deletion; do not label it read-only.

**Security-state query is insufficient:** `cpc/src/sl_cpc_system_secondary.c:680–695` reports `PROP_SECURITY_STATE` using `sl_cpc_security_get_state()`. The enum describes not-ready/disabled/initializing/resetting/session-initialized states, not a persistent bound/unbound bit. Both a bound radio awaiting a session and an unbound radio can be `INITIALIZING`.

`cpc/src/sl_cpc_security.c:725–740` returns `SL_STATUS_NOT_INITIALIZED` for `SESSION_INIT` when the in-memory `is_bound` flag is false. That is a useful protocol indication but is not a stronger storage-deletion check, and the normal CPCd startup path can create a host key when missing. Do not start a normal daemon or add a new session-probe tool merely to obtain this indication. The existing explicit unbind result provides the better bounded observable without a bind.

Storage corruption remains unsupported: `mbedtls/library/psa_crypto_storage.c:97–108` treats a definite `PSA_ERROR_DOES_NOT_EXIST` as absent and other metadata results as present; destroy verifies absence after removal. If ITS lookup/removal reports failure, the standard unbind command must fail and stop the branch. A no-object result only applies to this correctly matched SDK/backend's view; it is not proof an unknown/corrupt older store is healthy. Never convert errors into success or erase/reformat the store to make the check pass.

The normal candidate remains default-denied before and after recovery. The recovery image's permissive callback exists only during an explicitly approved maintenance flash on the trusted local serial connection; immediately return to the hashed candidate after a successful result. Leave the radio stopped and report failure if the return upload or subsequent single approved binding fails. Do not weaken permanent candidate security to simplify recovery.
