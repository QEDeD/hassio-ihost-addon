# Token compatibility result — 2026-09-19

The exact retained candidate image has a reproducible host-token migration defect. A narrow SDK patch fixes it in both the isolated source harness and the rebuilt final application ELF. The real retained baseline loader also preserves all26 original nonempty synthetic records and advanced counters on downgrade, but discards newer-only token content.

## Observed schema and preservation

Baseline input is **metadata only**, parsed read-only by the parent task on 2026-09-19 from `/backup/feec49c2.tar`, member `local_codex_ihost_otbr_focused.tar.gz`, nested `data/zigbeed/host_token.nvm`. No production token payload left HA. `baseline-backup-20260914.csv` contains 39 descriptors, 26 with nonzero array counts. `parse-v2-descriptors.awk` validates the complete v2 stream before printing ID, counter flag, element size and count.

Candidate image: `sha256:7f6104879bfe004823b03c3db5ba67d90ea1366d854372bba1732baa1e250f6b`. Its `/usr/local/bin/zigbeed` SHA256 is `0a88cad32c7e3010e922e2f60a5716a7693f65c0a426619d285d0ac8087968d8`.

Two independent entry points agree exactly on all 29 initialized candidate descriptors:

1. `extract-descriptors.c` compiles the actual generated `/sdk2026-recipe-zigbeed/zigbeed.project.mak` flags, vendor registration, host backend, configuration globals and strong configuration getters. It calls only `halStackInitTokens`, with an aborting assertion callback, never daemon/radio initialization. The weak simulation count defaults are overridden by the actual strong getters.
2. `elf-metadata-entry.c` intercepts libc startup of the exact final-image ELF and substitutes a metadata-only main. ELF offsets come from that binary's `nm`, with load address derived from the original main pointer. Original daemon main is never called. This runs in an isolated final-image container with `--network none`, no devices and no host volumes.

The candidate's actual initialized configuration gives binding=128, child=64, key=128, certificate=0, ZC/ZR=1. These are observed initialized globals, not guessed table-size macros or the weak test defaults. No application/EZSP session was simulated, and this does not prove every future runtime configuration has the same counts. `candidate-generated-defaults.csv` and `candidate-final-defaults.csv` match byte-for-byte.

## Actual defect and fix

`sl_zigbee_token.c` packs one default value per token into `tokenDefaults`, using each preceding token's element size as the offset. The host loader's rewrite loop instead used the token ordinal `i` as a byte offset. This supplies incorrect defaults when a record is new, enlarged, or reset for incompatible metadata.

A 6,395-byte synthetic file was generated from the baseline descriptor list with deterministic invented payloads. The exact candidate binary's loader preserved all 26 nonempty records but initialized all64 newly allocated `0x10880` elements incorrectly. Their documented default is the public constant `0x0f`. The new trust-center/key metadata and Multi-PAN child records happened to get their correct defaults; this does not make ordinal indexing valid.

`../../recipe/token-default-offset-sdk2026.patch` tracks `defaultOffset` as the sum of preceding element sizes. This changes only the source of default bytes, retaining file format, existing-record copying and registration order. It applies with `--fuzz=0` to SDK2026.6.1.

The source harness reproduces the original failure, then passes with the patch:

- All26 nonempty records preserved exactly, including network keys, both key-table segments, node/trust-center data, all four counter records and restored EUI64.
- All257 elements in the four new/expanded records match their vendor defaults after the patch.
- Before patch: regression exits8, with64 default mismatches. After patch: exits0, no mismatches.

Evidence: `exact-elf-default-checks.log`, `exact-elf-descriptors.csv`, `unpatched-result.json`, `patched-result.json`. The latter two come from the source harness. The original exact image remains unpatched. The parent integrated the patch and rebuilt image `sha256:f13e3adaea844f48f9e62b78ef92571a2c2b6790b3bc9da9799098638bf2e115`; its zigbeed ELF SHA256 is `983abe4ad018ce358e74e353b7ed5035f4733bbc86c70667631f3bf97a5ab530`. The same exact-ELF interception verifies all26 existing nonempty payloads preserved and all257 added/expanded elements correct. See `fixed-elf-result.json`, `fixed-elf-default-checks.log`, and `fixed-elf-descriptors.csv`. This is loader behavior evidence, not a physical network recovery test.

## Integration and reproduction

Apply the patch after SLC project generation and before compiling zigbeed in `review/sdk2026/recipe/build-in-container.sh`:

```sh
patch --batch --fuzz=0 -d "$sdk" -p1 < /recipe/token-default-offset-sdk2026.patch
```

The generated project directly compiles `$sdk/zigbee/stack/platform/sl_zigbee_token_host.c`; it does not copy this source into the project. The token worker did not edit the shared build script.

To reproduce the source regression in a dedicated SDK builder snapshot, put this directory at `/token-schema`, use the generated project directory as cwd, then:

```sh
make -s -f /token-schema/extract.mk extract-descriptors
# Before patch: explicitly expect the known defect.
python3 /token-schema/test-synthetic-migration.py --expect-default-defect
# Apply the patch, rebuild the same target, then require success.
python3 /token-schema/test-synthetic-migration.py
```

The test creates an isolated temporary working directory and synthetic host token file; it never reads live state. `extract-descriptors` without arguments outputs metadata and never initializes the backing file. Its `--synthetic-load` mode deliberately invokes the loader and must only be run in a disposable synthetic directory. Two numeric arguments can vary binding/key counts before registration for explicitly hypothetical configurations.

For the exact ELF check, use a fresh final-image container, copy only its non-secret ELF to the isolated builder, and generate the offsets header for `elf-metadata-entry.c`:

```sh
nm candidate-zigbeed | awk '$3 ~ /^(main|halStackInitTokens|sl_token_manager_get_data|sl_zigbee_get_token_default|sli_zigbee_token_count|tokenNvm3Keys|tokenSize|tokenIsCnt|tokenArraySize)$/ {print "#define OFFSET_" $3 " 0x" $1}' > elf-offsets.h
gcc -shared -fPIC -Wall -Wextra -o metadata-entry.so elf-metadata-entry.c -ldl
```

Confirm the ELF hash matches the intended image, copy the resulting shim back to its isolated image container, and invoke only that executable with `LD_PRELOAD=/metadata-entry.so`. Without arguments it prints descriptors; `--synthetic-load` loads the synthetic fixture and reports default comparisons. Never use the shim against a live daemon or real token directory. `make-synthetic.py` builds the deterministic fixture from CSV metadata only.

## Interpretation limits

This establishes descriptor compatibility and preservation of invented existing payloads in the candidate loader, including counter and restored-EUI64 bytes. It does not establish current counter freshness, network rejoin/communication, Zigbee stack semantics, or preservation after subsequent runtime commands.

The newly added additional-info types are uint32 with zero defaults. The visible security-manager source provides getters/setters and clears these fields when the corresponding trust-center/application-link key is deleted. It does not explain every consumer in the precompiled stack library. Therefore this check does not infer that zero has no operational consequence. Parent investigation retains that semantic gap.

The host restored-EUI64 implementation reads `0x1e12a` and uses it when nonblank; the synthetic migration preserves those bytes, but the real record's value was intentionally not inspected. No effective-radio-identity claim follows.

A backward **loader-only** round trip was executed with the actual rebuilt candidate ELF, then the retained baseline image `sha256:0224cb183592e0e83aac35ce9ed6f350654537b73b73c03b0ebb74a1f972b107` (tag `ghcr.io/qeded/otbr-integration-test-amd64:0.2.3-ordered`). Baseline zigbeed SHA256: `23895e1a6587d9d7febdcca82f8403d1145af5dda12fb12f787524dd64d83b9d`. Its token tables are static; `elf-baseline-entry.c` calls only its `initializeTokenSystem`, avoiding daemon main. Symbol sizes establish39 descriptors, matching archived baseline metadata exactly.

After candidate migration, the test advanced all four invented counters by1000 and populated all four new/expanded records with invented nonzero content. The actual old loader preserved all26 original nonempty records including those latest counters, network/link keys, and restored EUI64. It dropped the new trust-center/key additional-info records (4+512bytes) and shrank the new Multi-PAN child/additional-child arrays to0 (704+64bytes). Thus this path preserves the tested original network payloads but **does not preserve all state produced by newer firmware/features**. See `backward-result.json` and `baseline-elf-descriptors.csv`.

`test-backward-migration.py advance INPUT OUTPUT` creates the invented later candidate state from a synthetic migration file; `check LATEST BACKWARD` verifies preservation after the isolated baseline loader. Generate `baseline-elf-offsets.h` from the baseline binary with the same nm/awk method above using symbols `main|initializeTokenSystem|sl_zigbee_get_token_count|tokenNvm3Keys|tokenSize|tokenIsCnt|tokenArraySize`. Compile `elf-baseline-entry.c` as a shared library. Its entry point always rewrites the backing file, so use only a disposable synthetic directory.

Preserve original state and baseline host independently, and retain latest state before any downgrade. This does not authorize arbitrary downgrade or stale-counter restoration and is not a runtime network round trip.
