# Add opt-in NAT64 and host upstream DNS to Silicon Labs Multiprotocol

Current head: `4ff16428e8c8919d2c811f1feb59e07e20e8b766`. [Stacked diff against its firewall implementation base](https://github.com/QEDeD/hassio-ihost-addon/compare/60d3334daca697a57756b9492cdd6ac6f8f777ec...4ff16428e8c8919d2c811f1feb59e07e20e8b766). No PR has been submitted. The branch now includes firewall head 60d3334daca697a57756b9492cdd6ac6f8f777ec; the stacked comparison excludes that prerequisite. Its OTBR lifecycle code and s6 fixture match tested integration aca557b.

Add `otbr_nat64`, disabled by default, so compatible Thread clients can initiate connections to IPv4 services and forward DNS queries upstream. Ordinary local Matter operation does not require this option. It is independent of `otbr_firewall`; disabling ingress filtering does not enable IPv4 access.

This change depends on firewall lifecycle head `60d3334` and should be reviewed as a stacked change against that base. It follows the NAT64/upstream-DNS subset proposed by Arno500 in [iHost PR 78](https://github.com/iHost-Open-Source-Project/hassio-ihost-addon/pull/78). TREL and unrelated build changes remain outside this contribution.

## Behavior

- Reserve `192.168.255.0/24` while enabled. Before installing rules, refuse overlapping IPv4 interface networks or nondefault routes in any routing table, including narrower and covering routes. Default routes are allowed; conflicts are reported rather than removed. This startup check cannot detect conflicts introduced later.
- Permit IPv4 forwarding only from the Thread interface and reserved source pool to the selected backbone. Return traffic must be established or related. Masquerading matches the pool and backbone. Preserve global policies, unrelated rules and packet marks; never flush conntrack. Reconcile the owned chains on restart and disable, including stale duplicates or a changed backbone.
- Apply the saved setting after socket/REST prerequisites and before s6 readiness, once per agent incarnation. Explicitly disable both features first, then enable them when requested. Treat CLI `Error` output as failure even when the CLI exits zero; require `Done`. A failed or timed-out configuration stops the agent/container without advertising readiness. Configuration has an eight-second budget; ignored SIGTERM has a three-second bound, and shared firewall cleanup has a four-second budget.
- Route host-configured upstream DNS through the host routing table, including DNS reached over a separate bridge. The existing POSIX configuration header adapts the host-resolver policy accepted in [OpenThread PR 13545](https://github.com/openthread/openthread/pull/13545), without replacing compiler flags or importing the newer resolver implementation. This pinned resolver still supports IPv4 nameservers only, has no RDNSS path, and requires an infrastructure interface to exist.

This adds DNS forwarding, not a general DNS64 server. Compatible clients must synthesize IPv6 addresses from the advertised NAT64 prefix for IPv4-only destinations. After an in-process Thread factory reset, restart the app to reapply its saved setting; the startup checker is not a recurring reset monitor.

## Proposed acceptance boundary

The DNS comparison passed and its assertions/logs have been reviewed. The completed isolated gates make the change ready for upstream code review: the default remains off, the scope is explicit, and its build, lifecycle, packet and DNS behaviors have separate reproducible checks.

That review threshold does not waive physical production acceptance. Separate integration evidence: [combined AMD64 CI34747387036](https://github.com/QEDeD/hassio-ihost-addon/actions/runs/34747387036) passed at `0999946ab0c826b59ee599194f6dff49269b7b38` with all six contributions. This is evidence for that combined source/runtime, not an exact-head run of this individual branch. Local AMD64 wrappers subsequently passed full service-graph compilation, synthetic state continuity and runtime/browser checks; the ordered integrated image was published and trialled in production. The earlier light dropout also occurred on baseline; its final requested read was inconclusive. A later approved single candidate replay of the captured group-command sequence did not reproduce BUSY. Independent review found no new demonstrated candidate regression; the historical finding remains unresolved general Zigbee reliability work, without making another image switch mandatory solely for it. This does not establish candidate/baseline equivalence. AArch64 and ARMv7 build/linkage/native-web checks passed at integration 11bef36 in CI34749205311; physical ARM radio behavior was not tested. Host-reboot ordering remains unverified; subsequent shared-radio UDP evidence is described below. The initial combined trial kept NAT64 disabled. A subsequent approved test on the unchanged 0.2.3-ordered integrated image used a physical GRILLPLATS Thread plug: its correlated CASE rejection reached an IPv4 collector through NAT64, and a fresh reverse request on the same socket obtained a second correlated rejection. With NAT64 disabled on the same candidate, a fresh translated-source probe received no IPv4 response while ordinary IPv6 still passed and network data no longer advertised a NAT64 route. Independent packet review confirmed the identifiers and exact rejection bodies. This verifies that bounded UDP exchange; it does not verify DNS64, TCP or general Internet reachability. The final post-test observation completed with all three apps running in 21 samples over 629 seconds, changing Matter readings and a fresh closing Zigbee response. The candidate remains running with NAT64 off. The earlier BUSY cause remains unresolved; the bounded replay and its disposition are recorded separately in the integration evidence. Upstream submission and release remain subject to approval.
