# Trixie frontend and web-build dependency review — 2026-09-12

The completed AMD64 audit is positive build/linkage evidence for the existing SDK; this review found no reason to upgrade the SDK or rewrite the frontend as a prerequisite to Trixie. The most useful independent change is to preserve the **actual validated frontend dependency selection** in a lockfile. Copying the SDK's old lockfile unchanged would roll assets back. Boost is statically linked into the web binary; jsoncpp and protobuf-lite are dynamically linked. Java/SLC are generator inputs, not web/runtime features.

No production change, commit, build dispatch or application execution was performed. Review inputs were the local PR79 checkout Dockerfile, `trixie-audit-34707535921.log`, `trixie-upgrade-analysis-20260912.md`, exact pinned SDK source fetched from upstream, and primary documentation/public npm advisory data.

## What the npm warning establishes

The historical CI log has a summary of two vulnerabilities (one moderate, one high), not a retained npm audit JSON or exact dependency tree. It does **not** identify two CVEs. npm can aggregate multiple advisories under one package and report dependency propagation.

A fresh read-only request to npm's public bulk-advisory API on this review date for the seven apparent latest compatible direct versions returned ten advisory records under angular 1.8.3 and none under the other requested packages. This is a current package-level check, **not a reconstruction of the original audit**: Angular messages/D3/MDL exact resolved versions were not printed in the observed warning summary, and registry advisory data changes.

Examples returned include GHSA-4w4v-5hc9-xrr2 (ng-srcset-related ReDoS), GHSA-7x27-g8rg-x87w (SCE resource-URL policy bypass), and several sanitization/input/utility advisories. A focused source scan of index.html, join.dialog.html and app.js found no srcset, input type=url, angular.copy, ng-bind-html or explicit SCE policy configuration. That narrows obvious direct triggers; it does not establish non-exploitability through framework internals, templates or data flows. The frontend loads AngularJS in the browser, so removing npm from the image does not remove these assets or their advisory relevance. Debian/Node upgrades also do not patch npm-distributed AngularJS. Capture the exact audit JSON and map each advisory to actual inputs before choosing remediation; do not run npm audit fix --force blindly.

One concrete existing frontend issue is independent of Trixie: app.js constructs an HTTP api.qrserver.com QR-image URL containing the commissioning PSKd and eui64, then interpolates that URL into an Angular dialog template. Source establishes construction of an external HTTP image request containing credential data, and an unencoded value enters template construction. Whether a browser actually sends the request depends on execution and browser policy (including mixed-content handling); no credential disclosure or exploitability was demonstrated in this review. Keep this as a separately scoped finding. A local QR-generation option and binding a validated URL/value instead of concatenating template HTML would address the concrete flow more directly than an OS upgrade. Do not execute that QR action with real credentials during smoke tests.

## Acquisition observations

The inspected PR79 Dockerfile first COPYs slc_cli_linux.zip and then curl -O downloads the same filename from an unversioned URL. Therefore local archive presence alone does not pin the bytes actually used. Existing audit adaptations pinned SLC SHA256 5fc88e5f7e3a782a9181716bf173285d4794ea6d2282dde0c992179e3ab955f8 and source revisions; carry those controls into any reproducibility proposal instead of silently accepting the overwritten archive. Use failing HTTP/checksum verification and record a deliberate update process. The SDK tag/CPC tag and base image tags also need immutable revision/digest evidence. These acquisition improvements are separable from Debian compatibility.
